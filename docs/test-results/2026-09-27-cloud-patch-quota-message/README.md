# 2026-09-27 白天 · 修补版上云（release 20260927-1240：配额文案 + 建房来源 IP 进日志）

用户反馈：「为什么我这里显示同一来源最多创建三个房间？难道之前创建的都没有清掉吗？」

排查结论：**配额机制没有坏，是我的部署验收把它占满了**——但反馈暴露了两个真实的可改进点，本轮一并修掉并上云。

## 1. 排查过程与结论（先证伪"清理坏了"）

云端日志时间线（`journalctl -u listen-together`）：

| 时间 | 事件 | 说明 |
|---|---|---|
| 12:11:39 | `room.created C6C20BC3` | 用户手机上建的房间 |
| ≈12:27 | **部署 restart** | **清空全部房间**（含上面那个） |
| 12:27:47 | `room.created DBE5E981` | 我的部署验收探针 |
| 12:28:02 | `room.created 7EAA7E1E` | 我的 `m4-deploy-verify.sh` |
| 12:28:15 | `room.created CFE00423` | 同上 |
| 12:29:48 | `room.created 73BD0E2B` | 我试配额时**建房成功**——说明第 1 个已回收 |
| 12:32:47 / 12:33:03 / 12:33:15 / 12:34:49 | `room.deleted … empty-timeout` | 四个空房**逐个按点回收** |

- 机制（源码 `server/src/rooms/store.ts`）：房间空了以后**保留 5 分钟**供掉线重连（`EMPTY_ROOM_MS`），到期删除并释放配额；配额是**「同一来源 IP 同时活跃房间数 ≤ 3」**，不按历史累计；`restart` 清空全部房间。
- **因此"之前的房间没清掉"不成立**：用户此前的房间在部署 restart 时就被清了；紧接着我的三个验收空房把配额占满，用户这时建房才撞上 429。回收日志（4 条 `empty-timeout`）是清理正常工作的直接证据。

## 2. 因此修掉的两个真实问题

| 问题 | 后果 | 修法 |
|---|---|---|
| 429 文案只说「同一来源最多同时创建 3 个房间，请先使用已有房间」 | **没提空房 5 分钟后自动回收**，用户完全有理由认为配额只增不减 | 文案改为「…；空的房间保留 5 分钟后自动回收，请稍后重试或使用已有房间」，其中「5 分钟」由 `EMPTY_ROOM_MS / 60_000` 推导，避免常量改了文案不同步 |
| `room.created` 事件**不带来源 IP** | 排查时必须靠时间线反推"额度被谁占了"；本次排查因此多花了不少时间 | 事件增加 `creatorIp`；`src/events.ts` 的红线注释登记该例外（仅用于排障、不下发客户端、不参与身份判定） |

- 两条都补了**回归测试**：`rooms.test.ts` 断言文案同时含「最多同时创建 3 个房间」与「5 分钟后自动回收」（store 层与 HTTP 层各一处），并断言 `room.created` 带 `creatorIp`。
- 事件红线测试（禁令牌/昵称）不受影响：IP 不在禁用类别内，已用 `assert.doesNotMatch(/token|authorization|bearer/i)` 复核仍通过。
