## 为什么是三源而不是换源

对真实 23 首曲库做实测探针后的结论，不是偏好：

- **QQ 音乐**：`search_for_qq_cp` **一次请求**即返回标题/歌手/专辑/发行年/时长/专辑封面 mid，5/5 首中文歌的专辑与年份正确 → 定为默认源。
- **网易云音乐**：字段更杂（`ar`/`al`/`dt` 短键，`publishTime` 常为 0），且**榜首经常是翻唱 / AI 版本**（《句号》原唱在第 2 位）→ 保留为可选源，靠阈值与打分把翻唱压下去。
- **MusicBrainz**：华语覆盖弱、要两次请求（search + recording lookup），但**只有它给得出可读流派**，且有 release 级权威年份 → 保留。

三源归一到同一候选形状，**共用同一个 `scoreCandidate` 与同一个阈值**（默认 0.8）。国内平台不返回数值相关度，因此引入 `rankScore(index, total)`：把结果名次折算成相关度填进权重的 0.35 槽位——榜首且标题/歌手/时长全对 = 1.0，榜首但歌手不符（翻唱典型形态）= 0.75 < 阈值。这样"三源"没有变成"三套判定"。

## 出网边界（红线）

只发检索文本（歌名/歌手），只取回文本字段与封面 URL；**不下载音频、不注入任何登录 Cookie、不做批量爬站**。
限速：每源一条串行队列（MusicBrainz 约 1.1 秒/请求，QQ 与网易云约 0.8 秒/请求），批量由界面逐首调用后端点完成（每首独立成败，关页面不会留下半批写入）。
候选是外部不可信文本：界面一律 `textContent` 渲染，写库时读 `dataset` 值而非表格显示文字。

## 增补：删除曲目轮（2026-09-27 深夜）

用户指令："这个脚本上没有删除音乐的功能，请你加上"。三项决策由用户拍板：文件**移到回收目录**（不 `unlink`）、
连带处理**独立封面图片 + 歌词 `.lrc`**、粒度**单曲 + 批量都要**。

### 契约

`DELETE /api/tracks/:id?run=<批次名>&files=audio,cover,lyrics` → `{ok,id,title,moved,skipped,failed,trashDir,message}`。

| 参数/状态 | 口径 |
|---|---|
| `files` 白名单外的 kind | **400**（不接受 `audio/cover/lyrics` 之外的取值，臆造值也不放过） |
| `run` 带路径穿越（`..%2Fescape`） | **400**；`run` 受 `^[A-Za-z0-9._-]{1,64}$` 约束，回收目录名不可能逃出自建批次 |
| id 不存在 | **404** |
| 曲库当前就校验不过 | **409**「曲库当前校验不通过，未改动任何文件（请先修好曲库再删）」 |
| 移除条目后整库校验失败 | **422** + catalog 逐字节回滚 |
| 移文件失败（跨分区/权限） | 先退化为复制后删；仍失败只进 `failed[]` 如实上报，**条目删除照常成立** |

**顺序是硬约束**：闸门先行（`loadCatalog` 自检）→ 移除条目并过 `writeAndValidate` → **才**动文件。
反过来的失败态是"catalog 还引用着一份已消失的 MP3"，后端下次启动直接失败，比删不掉严重得多。
409/422 分工：409 = 库本来就是坏的（这次没碰它）；422 = 这次写把它改坏了、已回滚。

### 回收目录与引用计数

- 落点 `TRASH_DIR/<批次>/<库内相对路径>`（默认 `.workbuddy/media-trash`，新增 `--trash` 可挪根）+ 每批一份
  `manifest.jsonl`：`{at,id,title,catalogEntry,moved:[{kind,from,to}],skipped:[{kind,reason}],failed:[{kind,path,message}]}`。
  被删条目**原文**在 manifest 里，放回不必凭记忆重填字段；相对路径保留，一眼对得上。
- 三类文件**都按引用计数**决定归属（`otherReferrers(entries, entry, field)`，realpath 归一后比对）：
  只有独占文件随曲目进回收目录；被别的曲目共用的留原地并在 `skipped` 点名"谁还在引用"。
  `covers/` 之外的封面路径只删条目不动文件——工具只回收自己放进去的东西。
- 夹具造的关系：track-a/track-b 共用一份 `.lrc`；track-a/track-c 共用一张走接口上传的独立封面；
  track-c/track-d 共用同一个 `.mp3`；track-d 的 `cover` 手写指向库根 `stray.png`。
