## 需求范围与实施默认值

原设计记录的需求：成员及房主都可以点歌；点歌追加到队尾，不替换当前播放。支持随机加入歌曲。房间内提供即时文字聊天。曲库将扩展至几百至上千首，可以参考 GitHub 开源实现。用户本轮要求补齐文档；功能开发由后续明确的启动指令触发。

实施默认值（按本文启动开发时采用，后续用户明确指令可覆盖）：房主控制共享播放、跳过和队列顺序；成员可撤回自己未播放的点歌。待播队列最多 100 首，普通成员同时待播最多 5 首，当前曲不计待播配额；随机添加 1 首或 5 首也受配额约束。同一歌曲已在当前播放或待播队列时不重复加入；播放完后允许再次点。队列耗尽停止，不自动把全曲库接着播放。任何无当前曲的状态下加入歌曲，首曲成为当前曲并保持暂停，房主点击播放后开始。

聊天仅纯文本，保留本房间最近 100 条内存消息，房间销毁或服务重启即清空；重连时可恢复仍在窗口内的消息。第一版不加入图片、语音、私聊、@、已读状态、长期历史或推送。

## 为什么必须拆开曲库与队列

当前 ui.tracks 同时表示总曲库与播放顺序。服务端 tick 按全曲库 index+1 顺播，客户端 TrackQueue.skip 也在全曲库中选上下首。这种耦合必须同时在两端解除，仅在界面隐藏曲库不足以实现房间点歌。

总曲库 Catalog 是可搜索、可分页的资源集合；房间队列 Queue 是有序的点歌条目集合；当前播放 NowPlaying 持有一个条目与权威时间线。聊天 Chat 是独立的消息流。

现有 LazyColumn 已按可见范围组合条目，一千首不意味着一千行同时渲染。仍需关注封面解码、重组范围、检索和响应大小；可参考 [Android 惰性列表文档](https://developer.android.com/develop/ui/compose/lists) 和 [Paging 文档](https://developer.android.com/topic/libraries/architecture/paging/v3-overview)。

## 数据模型与状态所有权

实施时按以下职责建立领域模型（内部类型名可依项目惯例调整）：

- CatalogIndex：revision、tracksById: Map、可检索元数据数组。曲目查询平均 O(1)，取代当前播放路径中反复线性 find/findIndex。
- QueueEntry：entryId、trackId、requestedByMemberId、requestedByName、requestedAtMs、source（manual/random）。
- NowPlaying：当前 QueueEntry（保留点歌人快照）、完整公开曲目元数据，以及 playing、positionMs、timestampMs。沿用 state.version：成员或播放状态改变时递增；它不是纯播放命令计数。点歌追加和聊天不得使它递增，queueVersion/chatSeq 分别独立。
- RoomQueue：entries、queueVersion，当前曲独立于待播 entries；点歌只修改队列，不重置当前曲时间基准。
- ChatMessage：messageId、seq、senderId、senderName、text、createdAtMs、clientMessageId。昵称和发送者从认证身份取，客户端不能指定。
- ChatState：最近 100 条消息与递增 chatSeq。与播放 version、queueVersion 分开。

请求去重 ID 与业务 ID 分开：requestId/clientMessageId 是客户端某次操作的身份；entryId/messageId 是服务端确认后的条目身份；trackId 是资源身份。重试同一次操作不应产生第二条队列项或聊天消息。

## 界面与检索流程

房间主内容使用“队列 / 点歌 / 聊天”三个页面，底部迷你播放器保持常驻。“队列”只展示本房间待播歌曲及点歌人。“点歌”提供歌名/歌手搜索、按页浏览、“加入队列”和“随机加 1 首 / 5 首”。默认先展示有限数量结果，不把全部歌曲放到房间首页。

检索默认：输入 debounce 300ms，取消旧请求，同时用查询代次拒绝迟到结果。曲库分页默认 30 首，上限 50 首；按规范化歌名、歌手、trackId 依次稳定排序，附 catalogRevision。曲库版本变更时放弃旧分页结果，避免跨版本拼接。offset 为非负安全整数，limit 为 1–50 的整数，非法参数返回 400；q 最多 100 个 Unicode 码点，空查询按上述排序浏览。查询和字段统一 NFKC、转小写、合并空白后做子串匹配，不加入拼音搜索。

千首量级首版采用服务端内存元数据索引和 O(N) 文本过滤，无须搜索集群。歌名/歌手按上述规则规范化；拼音检索留到另行需求，不属于本轮。album/year/genre 当前播放后端未完整消费，不作为第一阶段检索的必要条件。

拟议 HTTP：
GET /api/rooms/:code/catalog/search?q=...&offset=0&limit=30
返回 catalogRevision、total、offset、items。仍要求成员 Bearer 鉴权，不返回文件路径。

分页不能破坏播放：v2 当前曲目公开元数据随播放 state 提供，空曲目为 null；复用 catalog 的公开元数据字段，绝不直接序列化服务端 Track（含路径/图片字节）。PlaybackService 不再依赖“当前歌曲恰好存在于已加载搜索页的 ui.tracks”。catalogRevision 根据公开编目内容生成，包含封面/歌词版本，不用每请求变化的时间戳；分页请求带已有 revision 时，不匹配返回 409 CATALOG_CHANGED，客户端清页重查。

## 点歌与随机加入

所有有效房间成员可 queue.add；服务端确认曲目存在、重复规则与容量，生成条目并追加。多成员同时点歌的 FIFO 定义为服务端接受顺序，不依赖手机时间戳。状态修改保持同步、无 await；若以后接入异步存储，使用每房间串行执行或事务。

随机选择必须由服务端从完整曲库执行，而不是从客户端当前搜索页选。候选集合排除当前曲和待播曲，采用不放回抽样；同一批次不重复。若候选或配额不足，允许添加实际可添加数量并返回 addedCount；零首则返回明确原因。去重缓存中保存已抽中的结果，重试不能重新抽一批。

普通成员可移除自己未播放的点歌；房主可移除任意待播条目、调整顺序、跳过当前曲。重新排序使用 entryId 和锚点，以及 expectedQueueVersion，避免旧界面覆盖别人刚加入的歌曲。发生版本冲突回明确错误并发最新队列，客户端按新状态显示。

初始默认限制：队列 100 首、普通成员 5 首待播。房主可不受个人待播上限，但受队列总容量限制。空队列随机加 5 首时，1 首成为暂停的当前曲、4 首待播；抽样数量必须先依据最终待播占用计算。点歌独立限频，具体规则见下文；房主降为普通成员时不删已有点歌，超过个人上限期间只禁止继续添加。

## 播放推进与边界规则

当前曲结束：服务端从待播队头取下一项，建立新的 positionMs=0、timestampMs=now，继续播放。没有下一项则清空当前播放并停止。手动跳过同样由服务端取下一项，保留原先播放/暂停意图。

首次空房或耗尽后再次点歌：第一项成为当前曲并保持暂停，其余留在队列；房主明确播放后启动。用户主动暂停时后续点歌不恢复声音。成员自己的 locallyPaused 仍具有最高优先级。建房从无当前曲开始，不预选全库第一首。

现有通知栏“下一首”必须改成服务端 skip-next，不能再由客户端根据全曲库计算 trackId。第一版“上一首”固定为回到当前曲开头，保留播放/暂停意图；应用内标为“回到开头”，不实现播放历史。v2 禁止 select 绕过队列；房主要切换歌曲也须入队/调整队列/跳过。

| 触发 | 当前曲/待播变化 | 共享播放结果 |
|---|---|---|
| 当前曲为空时点歌 | 第一项提升为当前曲，其余追加 | positionMs=0、playing=false |
| 有当前曲时点歌/撤回/排序 | 仅改待播队列 | 时间基准、播放状态不变 |
| 自然曲终且有有效待播 | 消费队头，换新 entryId | positionMs=0、playing=true |
| 房主跳过且有有效待播 | 消费队头，换新 entryId | positionMs=0、保留原 playing |
| 曲终或跳过且无有效待播 | 当前曲与待播清空 | positionMs=0、playing=false |
| 没有当前曲时播放/跳过/回到开头 | 不改变状态 | 返回 409 NO_CURRENT_TRACK |

当前曲清空时，Android 必须 pause/stop、clearMediaItems、复位实际倍速、清旧封面/歌词/时长与待确认 seek；通知栏不得保留旧曲标题或可用的切歌按钮。保留房间连接及聊天，不能因清媒体项自动退出房间。以后同一 trackId 再次入队必须按新的 entryId 建立一次播放；媒体身份和资源缓存键分开，资源缓存仍用 trackId 与内容版本。

房主变化不清队列，不清聊天。点歌人离房保留已点歌曲。取下一首时跳过服务端已知不存在或已标记失效的条目，返回可见提示，扫描次数受队列长度上限约束；领域操作内不 await 文件探测。单个客户端的断网/解码失败不能让它擅自替全房跳歌，继续沿用本地播放失败提示；运行期文件故障需由服务端证据确认后标记，未确认时房主可显式跳过。

当前基线尚无曲库热加载。分离出 CatalogIndex 可为后续版本切换预留边界，但本功能阶段不能宣称已解决热更新与重启清房问题。

## 协议拆分与操作确认

沿用现有 WebSocket，每条消息拥有独立 type。拟议客户端操作：
- queue.add：requestId、trackId。
- queue.addRandom：requestId、count（仅 1 或 5）。
- queue.remove：requestId、entryId。
- queue.move：requestId、entryId、beforeEntryId（可为 null）、expectedQueueVersion。
- command/skip-next：requestId，房主权限。
- chat.send：clientMessageId、text。
- queue.sync / chat.sync：主动恢复快照；聊天可携带 lastSeq。

拟议服务端事件：
- state：播放状态与当前曲元数据，保持校时语义。
- queue.state：queueVersion、待播 entries（带显示所需元数据），仅加入/重连、队列改变或显式请求时下发。
- chat.message：一条已确认消息；包含 seq 和 clientMessageId。
- chat.snapshot：保留窗口内的消息、latestSeq、oldestSeq，用于入房/重连。
- ack：requestId/clientMessageId 对应的确认结果；错误附关联 ID，客户端能定位失败操作。

队列有界，第一版使用完整队列快照即可；不需要同时实现复杂增量队列协议。聊天使用逐条事件，加重连快照，不能每 5 秒将整个聊天历史重新塞入播放 state。

所有 v2 WS 有副作用操作（包括播放命令）统一带操作 ID 和 issuedAtMs（客户端估计的服务端时间，需先校时）；chat.send 使用 clientMessageId，其余使用 requestId。ID 为 UUID，重试保留原 ID、时间与输入。去重键为房间+成员+ID，指纹含消息 type/action、issuedAtMs 与规范化业务输入；同 ID 不同输入返回 409 IDEMPOTENCY_CONFLICT。业务状态和去重确认记录在同一同步临界区提交，广播失败不撤销已提交结果。HTTP 建房/加入的既有行为不因此自动获得去重保证。

有效期固定为 issuedAtMs+10 分钟；首次接收拒绝超过未来 30 秒或已过期的时间，过期返回 409 REQUEST_EXPIRED，绝不重新执行。返回确认带 expiresAtMs，客户端不能通过刷新原操作时间延长重试期限。服务端先鉴权、检查现存去重记录，再校验首次请求的时间/限额；重连仅在原成员身份仍有效时复用记录。过期、退出、换房或身份失效后丢弃自动发送资格，未确认操作提示核对当前状态，不自动换 ID 补发。

去重默认每房间最多 10000 项，序列化记录总量最多 4MiB，全服最多 64MiB（还需在 D 阶段实测 JS 对象开销）。只保存指纹与紧凑确认结果，不重复保存聊天原文或整份快照；结果最多 5 个 entryId 或一个 messageId/seq。**未过期记录不得因 LRU 或容量压力提前淘汰**；提交前预留容量，满时拒绝新操作并返回 429 DEDUP_CAPACITY，不产生副作用，已记录操作的重试仍可返回原结果。清理过期记录、房间销毁时释放计数；时间源可注入，并测试服务端时间回拨时不会重新执行已淘汰的过期请求（操作有效期使用不倒退的服务端时基，不改播放校时公式）。

去重结果覆盖已通过身份/schema/时间校验并获预留容量后的确定性业务成功或失败。解析错误、限频、容量不足不占结果槽位且无副作用；这些操作可在未过期时用原 ID 重试。已缓存业务失败如队列满，不会因条件变化变成成功；用户再次点击是新的操作。客户端确认超时为 5 秒：请求一次对应状态恢复，并显示待确认/重试入口，不自动重放操作。

发送确认丢失时，客户端显示待确认或失败并允许用同 ID 重试；不在重连后盲目重放所有点歌/聊天。聊天用 messageId/seq 去重；超出保留窗口应提示中间消息不可恢复，不承诺永久或严格 exactly-once 投递。

客户端点歌展示“正在加入”，服务端确认后才出现正式条目。聊天可先显示 pending 气泡，收到确认替换；发送失败保留文本和重试入口。

## 聊天细节

服务端统一生成消息 ID、顺序号和时间戳；同一房间按服务端接受顺序展示。纯文本渲染，不解析 HTML，不在后台自动朗读、播放音效或推送。

默认限长 500 个 Unicode 码点，另加 UTF-8 文本字节上限 2048，并遵守现有单条 WS 输入帧 4096 字节上限；空白消息拒绝，允许换行和普通表情。测试中文、emoji、组合字符及 JSON 转义后的帧长度，不能把 UTF-16 length 简单当作“字”。

每成员聊天最多 10 秒 5 条，超过后明确回错误；限频不消耗播放/校时额度。身份由握手及当前成员校验得出，不接受客户端伪造昵称和发送者字段。

聊天室使用 LazyColumn 与稳定 messageId key。用户在底部时自动滚到新消息；用户在翻旧消息时不抢滚动，展示“有新消息”。切回聊天页时显示未读数，退出房间清掉当前聊天状态。草稿随页面切换保留，但不得被发送到另一个房间。

## 安卓状态拆分

RoomClient 继续负责会话、认证与 WS 路由，可逐步拆出：
- roomState：连接、成员、播放状态；原同步流程继续使用。
- queueState：队列与 queueVersion。
- chatState：聊天缓冲、未读与待确认消息。
- CatalogRepository：检索请求、分页与元数据缓存。

PlaybackService 只观察影响播放的状态。收到 chat.message 或仅有队列追加时不得触发播放器重新加载、seek 或变速；UI 不因 500ms 进度采样重组聊天和整个歌单。

generation 保护要扩展到检索、聊天确认与队列响应。旧房间迟到响应、旧搜索结果、旧 pending 消息不能污染新会话。长连接保持原有重连/心跳/慢客户端关闭逻辑，不另建聊天连接。

## 千首曲库的资源边界

现有服务端在 loadCatalog 时 Promise.all 解析所有音频，并把封面原始字节常驻内存；每图最大 1MB 不代表总量有界。上千张图的理论累计量可达约 1GB，分页客户端无法解决服务端这一点。

真实曲库扩至千首之前必须完成 D 阶段：
- 封面按需读取与总容量有界缓存；catalog 保留图片路径与版本元数据，不把整库图片永久常驻。
- 音频解析默认最多 4 路并发；预计算时长/媒体元数据的磁盘缓存作为后续优化，不要求本轮改管理器上传流程。
- 曲目 ID Map，播放 tick 不随曲库数量反复线性扫描。
- Android 缩略图降采样和内存 LRU 保留；仅加载可见条目资源。
- 千首/两千首夹具验证启动耗时、内存、搜索和滚动。大规模图片可使用重复生成夹具，不需要复制真实版权音频。

SQLite 可作为后续编目与索引演进，但千首数量本身不足以迫使第一版迁移数据库。房间队列和聊天可继续随现有房间保持内存生命周期。

### 版本兼容与切换方案（B 阶段必做）

采用明确的 v2 切换，不长期维护两套房间播放顺序。A 阶段只做本地基础重构，v1 行为和消息不变，不独立发布半成品协议。B 完成后新后端只创建 v2 队列房间；C 再增加聊天能力。

| 客户端/后端组合 | 必须表现 |
|---|---|
| 旧 APK + 旧后端 | 保持原有基线 |
| 新 APK + 旧后端 | 建房/加入前探测能力；缺能力返回本地可理解的“不支持点歌队列，请升级服务端”，不建房、不进入 WS 无限重连 |
| 旧 APK + 新后端 | 建房/加入/WS 握手返回 426，正文保留 message 字段提示升级；不能以旧 select 控制 v2 房间 |
| 新 APK + 新后端 | 能力匹配后正常入房；B 版 chat=false 时隐藏聊天页，C 版 chat=true 才展示 |
| 新 APK 会话中后端回滚 | 重连先重新检查能力，不重放命令；不兼容转终态并给出提示 |

新增只读 GET /api/capabilities，返回支持的协议版本、功能标志（queue、catalogSearch、chat）与 serverNowMs，不暴露成员或路径。v2 建房/加入/受保护的业务 HTTP/WS 握手携带 X-ListenTogether-Protocol: 2；缺失或不支持的版本返回 426 PROTOCOL_UNSUPPORTED，校验先于创建成员。health、能力探测、已鉴权的媒体资源与退出清理保持现有可用语义；旧全量 catalog 路径保留，但在 B 后同样要求 v2，供诊断脚本迁移，不再供新 APK 首屏全量加载。

新 APK 能力探测遇 404 表示旧服务端；超时/网络错误走可重试连接失败，不能冒充版本不兼容。协议版本按支持集合判定，功能按标志判定，不比较日期字符串或简单认定“版本越大越兼容”。HTTP 426 和 WS 升级失败 426 均转兼容性终态；新 state 含协议标识，意外收到旧格式也停止跟随。旧 APK 的实际错误展示需用旧包或已有解析器复测，不宣称旧包具备新升级页面。

正式切换要配套新 APK、后端制品、更新后的 member/load/验收脚本及回滚说明。发布前确认无活跃房间；后端重启清房属于既有边界。回滚需要匹配旧 APK，或者新 APK 明确停在不兼容提示；不允许回滚后悄悄恢复全曲库选歌。云端发布另按用户授权与部署手册执行。

### 限流、快照与恢复的实现约束

1. v2 把当前“每连接所有消息共享每秒 20 条”改为分类配额：聊天每成员 10 秒 5 条；queue.add/addRandom/remove/move 合计每成员 10 秒 5 次；房主播放命令每成员每秒 10 次；sync、queue.sync、chat.sync 各自每成员每秒 2 次。采用滑动窗口，重连不清成员配额；429 带 retryAfterMs 和已校验的关联 ID。重复请求可返回已缓存确认，不重复消耗业务配额，但仍受传输滥用防护。
2. WS ping/pong 控制帧不进业务配额。另保留每连接每秒 100 条输入消息的硬保护（含未知/重复消息），超出以 1008 关闭该连接；严重滥用导致该连接断开是明确边界，不承诺无限刷屏下保持其校时。业务限频测试与硬保护测试分开，其他成员不受影响。schema 校验错误不能广播，错误响应同样受发送容量约束。
3. 输入帧保持 4096 字节。输出队列/聊天是**逻辑完整快照**，按实际 JSON UTF-8 字节分块，每块最多 32KiB，带 snapshotId、chunkIndex、chunkCount、同一 queueVersion 或 latestSeq。100 条长中文/emoji 聊天不能一次性塞进单帧后立即连发多份快照。
4. 保留 socket 128KiB 慢客户端保护；发送前计入本帧字节，按发送回调/缓冲回落继续分块。应用层待发总量每连接最多 512KiB，全服最多 64MiB；队列满关闭慢连接 1013，不能无限排队。一个客户端发送失败不能打断其他成员广播或回滚领域状态；不要用固定 sleep 猜测网络已发送完。
5. 同类快照传输期间新的 queue.sync/chat.sync 合并为一次后续恢复，禁止复制堆积。快照来自同一时刻的副本；客户端收到全部块后原子替换，缺块/超时 5 秒则丢弃并请求一次恢复，持续失败走正常重连退避。快照后续事件按发送顺序排在快照后；客户端拒绝旧会话/旧 snapshotId，较低 queueVersion 不回写。客户端组装每份快照最多 512KiB，不能因服务端错误无限分配。
6. chat.sync 首版始终回当前保留窗口的快照；lastSeq 仅用于判断缺口。空历史 oldestSeq=null、latestSeq=0；lastSeq 小于 oldestSeq-1 时 gap=true，提示遗漏不可恢复；等于 oldestSeq-1 时没有缺口。聊天确认可早于或晚于广播到达，pending 以 senderId+clientMessageId 对齐，再用 messageId/seq 去重。ack 只含消息身份时，可先确认本地气泡并同步快照，不能伪造服务端时间或顺序。seq 缺口先恢复快照，不能把乱序内容当作全量历史。

以上默认值是实现起点，D 阶段只允许依据实测调整资源/限流常量并记录原因；播放同步阈值不在调整范围。正式字段、错误枚举及分块 schema 必须在实现前落入 protocol.md 并由实际输入/输出契约测试验证。

### 界面与操作反馈补充

- 沿用现有 Compose/Material3 样式，默认进入队列页；当前曲展示于常驻播放器，空队列提供去点歌入口。成员无房主控制权限时不显示可点击的共享跳过/排序操作，自己的本机暂停/恢复跟听保留。
- 重排首版用“上移/下移”按钮实现 entryId+锚点操作，不要求拖拽库；冲突刷新后由用户重新操作，不静默重放旧排序。加入/发送处理中提供反馈，按钮禁用避免重复点击，但服务器仍必须独立去重。
- 聊天草稿与 pending 绑定会话代次；换页保留，退出房间清除。首屏历史不计新未读；未读只计他人新消息，用户回到底部才清零。自己发送成功滚到底部；翻阅历史时他人新消息不抢滚动。
- 输入法弹出时输入框和发送按钮必须可见，处理系统栏/键盘 inset；小屏、2 倍字号、长昵称、长中文、emoji、多行草稿和播放器展开/收起列入设备验收。触控目标至少 48dp，图标有可访问标签，不能仅靠颜色表示 pending/失败。这些是通用交互验收要求，具体布局仍需真机验证。

## 分阶段交付与验收

阶段 A：建立 CatalogIndex、内部当前曲公开元数据模型与检索分页，为 B 做准备；保留原有 v1 行为/序列化，不能在缺少 v2 能力协商时改变在产协议。先用元数据夹具验证千首过滤与分页、旧查询隔离；“未搜索歌曲播放”的端到端验收随 B 的 v2 state 一起完成。

阶段 B：共享点歌队列、随机加歌、房主管理与通知栏下一首。至少覆盖两成员并发点歌、同 requestId 重试、两人点同曲、删除权限、重排冲突、首次点歌、暂停时追加、最后一首结束、曲目失效、房主转移、断线后队列一致。同步校时公式和纠偏参数本阶段保持不变。

阶段 C：即时文字聊天。覆盖隔房广播、伪造发送者、空白/超长/中文/emoji、独立限频、发送确认丢失、重试去重、重连恢复、窗口截断、换房迟到消息、翻历史时不抢滚动。15 人并行聊天和点歌时，播放命令与心跳仍可正常处理。

阶段 D：规模与性能采用 R8 benchmark 口径（正式 release 仍拒绝当前明文 IP）。完成封面按需读取、默认 32MiB 的全服图片字节 LRU（按字节计费）、最多 4 路音频解析；保留独立封面优先/ID3 回退与 coverVer、lyricsVer 失效语义。读取 ID3 内嵌封面也要限并发并合并同资源在途读取，不能启动时解析完又永久持有图片；不在本轮引入数据库或曲库热加载。

规模验收使用隔离的 1000/2000 首合成媒体夹具，覆盖独立图/内嵌图/无图/近 1MiB 图片与歌词，不改真实 media/。记录硬件、Node/Android/制品版本、冷启动耗时、峰值 RSS/heap/external、解析峰值并发、图片缓存峰值和清退后的稳定值。搜索用固定查询集（空、精确、部分、无命中、中文/英文），预热后至少 1000 次，服务端处理耗时 p95 ≤100ms，不含网络；完整报告错误率，不能只排除慢请求。缓存字节和解析并发不得超过配置；进程总 RSS 与启动时长须报告实测及机器内存余量，不在没有数据时宣称达标。

首屏在相同视口下仅请求第一页和可见资源，1000→2000 首不能让请求数翻倍。15 成员混合负载至少持续 10 分钟，聊天按配额发送、交错点歌/撤回/播放/校时，合法请求不得被错误限频，队列/消息顺序及权限正确；记录校时 RTT、命令确认 p95、断线/错误、事件循环延迟。另跑超过业务配额但低于硬保护的单成员刷屏、满 100 条长消息的慢网重连恢复，验证不误踢正常客户端、不拖累其他成员。

“不干扰播放”分两层：确定性测试中，单独派发 chat.message 或仅待播变化，播放器 load/seek/变速调用增量为 0；有同步定时器的集成/设备测试允许正常纠偏，比较同设备/同曲目/同网络下有无聊天负载的纠偏次数、漂移、缓冲与掉帧，报告原始数据。不能要求持续播放时纠偏总数为零，也不能把模拟器测量冒充双真机同步结论。

完成每阶段时同步源码、测试、模块文档和 verification.md，记录实际覆盖与未覆盖的设备场景，不用脚本 WS 成功替代声音同步结论。
